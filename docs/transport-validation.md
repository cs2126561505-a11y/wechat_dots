# 普通微信群通道验证计划

目的：以最小投入确认可用的读写通道，再连接原 ChatGPT dot。已完成首轮群读取，完整通道仍待验收。

## 当前优先路线：保留微信 4.1.15.13

2026-10-17 决策：优先审查 `wechatauto-replica 1.2.6.1` 的固定提交 `62503d7`。专用来宾已完成首轮读取，取得唯一群 ID、发送者身份和真实 @ 的正向元数据；普通/假 @ 的字段缺失语义、断线恢复及发送目标绑定仍待验证。探针默认关闭，实时读取需短时私密准入；发送保持关闭。[源码审查](replica-audit.md) · [操作说明](probe-guide.md)

日常电脑同时保存主账号和测试账号目录，且密钥提取会扫描进程内存。因此所有者已选择仅登录测试账号的专用 Windows 虚拟机或备用电脑。先审查该环境的文件、进程与共享资源边界，再决定是否放行只读测试。严禁把 Python 虚拟环境或指定账号目录视为完整隔离。A、B 两条路线作为备选保留，不为此次实验降级日常微信。

## 准入 A：WeChatFerry

在独立 Windows 环境中确认可追溯的 WeChatFerry 安装包、配套微信版本和正常登录条件。上游当前归档，发布页标注 `v39.5.2` 配套 `3.9.12.51`，测试记录据此明确实际组合。[发布页](https://github.com/lich0821/WeChatFerry/releases/latest)

先由所有者登录测试账号，再用适配器读取登录状态和群事件。获得消息、群与成员身份，以及真实 @ 元数据后，向同一个普通群发送一条所有者批准的固定文本。这个探针只验证传输，暂时保持模型链路关闭。

通过标准是登录、群接收、身份字段、触发元数据和原群发送均有实测证据。出现客户端版本拒绝、登录失败或关键字段缺失时，记录阻塞项并暂停该版本。维护分支需提供新的版本映射和同一套实测证据。

## 准入 B：Wechaty + 具体 Puppet

先确定 Puppet 名称、版本、协议、运行环境和维护入口。PadLocal 路线优先确认供应方仍可发放可用凭据，说明有效期、价格、兼容版本与数据处理路径，再用测试账号演示普通群收发。申请入口的 2026 年问题报告作为采购前核查项。[PadLocal 文档](https://wechaty.js.org/docs/puppet-providers/padlocal/) · [入口报告](https://github.com/wechaty/puppet-padlocal/issues/382)

有可用凭据后再编写最小 Wechaty 探针。检查群消息事件、稳定群 ID、实际成员 ID、真实 @ 和原群回复。凭据或服务状态待确认时，将此路线保持在供应方核查阶段，暂缓付费和框架集成。

XP 属于 Windows 路线。采用它时复用准入 A 的环境检查，并按 XP 的版本表选择客户端。[XP 版本表](https://github.com/wechaty/puppet-xp#version-support)

## 共同收发测试

使用一个已获授权的普通微信群与所有者控制的测试账号，测试正文采用合成内容。真实标识和详细日志保留在私密环境，公开记录使用稳定脱敏标识。

| 场景 | 核查内容 | 通过标准 |
| --- | --- | --- |
| 群内文本与真实 @ | 普通消息、真实 @ 和正文伪造 @ 分开发送，观察授权范围内的回调 | 正确识别群、成员与平台 @ 元数据；仅真实触发进入 dot 队列 |
| 原群回复 | 批准一条带唯一测试标记的固定文本 | 回复出现在来源普通群，收件目标由可信事件绑定 |
| 自身消息 | 观察适配器接收自己发出的测试回复 | 自身消息被识别并从唤醒链排除 |
| 去重 | 在测试网关中重复投递同一已捕获事件 | 持久化事件复用，发送记录保持唯一 |
| 断线恢复 | 主动停止连接后恢复，核对前后消息和登录状态 | 记录缺口和恢复结果，按消息有效期处理 |
| 身份碰撞 | 使用相同显示昵称、群名或引用文本构造测试数据 | 路由与授权依据平台身份字段而非显示文本 |
| 停止 | 所有者触发管理入口的暂停操作 | 后续事件与发送暂停 |

收发能力与网关控制分别记录。前两项确认传输可用；去重、授权和停止验证后续网关实现。基础链路通过后，可增加 24 小时低频观察，记录掉线、延迟、消息缺口和重复情况。该观察是计划中的测试窗口。

## 与 dot 连通

选定通过准入和基础收发测试的通道，再连接已部署的 MCP Events 服务。先投递合成事件，确认指定 dot 被唤醒并生成草稿；再以真实 @ 触发测试，审核后发回来源群。[网关架构](architecture.md)

现阶段继续核查缺少 @ 字段的语义、断线恢复及目标绑定。若关键前提无法成立，记录候选未通过并继续评估其他通道，保留日常客户端版本。具备新的兼容环境或可用 Puppet 凭据后，可恢复 A、B 路线的验证。
